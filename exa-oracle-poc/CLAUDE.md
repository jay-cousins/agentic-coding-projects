# Claude.md

## Project

A staging/review UI for the EXA oracle: it fetches structured, source-grounded
datapoints from the Exa Search API (US Open result, Copernicus climate
bulletin), stages each result for human approve/reject, and only appends
approved results to the shared `oracle_output.jsonl` log. The frontend
(`web/`) and the root Python script (`web_scrape_source.py`) both read/write
that same file.

`EXA_API_KEY` is required — set it in `web/.env.local` for the frontend (see
`web/.env.example`) and in the root `.env` for the Python script. No default
exists; get one from your Exa dashboard.

## Commands

### Backend (root directory)

- `python3 web_scrape_source.py` - Run the original CLI fetcher/writer. Writes
  directly to `oracle_output.jsonl` with no approve/reject step. Requires
  `EXA_API_KEY`.
- `pip install -r requirements.txt -r requirements-dev.txt && python3 -m pytest` -
  Run the backend test suite (`tests/test_web_scrape_source.py`).

### Frontend ( `web/` directory)

- `npm run dev` - Run the development server (localhost:3000)
- `npm run build` - Production build
- `npm run lint` - ESLint
- `npx tsc --noEmit` - Type-check
- `npm test` - Run the frontend test suite (Vitest; unit tests for `lib/`
  and `app/api/**` route handlers)
- `Ctrl+C` - Stop the development server in the terminal where it's running
- `lsof -ti:3000 | xargs kill` - Stop the development server if it was started in the background

## Code style

- Use 2-space indentation. There's no Prettier or `.editorconfig` — `npm run
  lint` (`eslint-config-next`, `core-web-vitals` + `typescript`) is the only
  enforcement, so match surrounding formatting by hand.
- Prefer named exports. Use `export default` only where Next.js requires it:
  `app/page.tsx`, `app/layout.tsx`, `app/error.tsx`.
- Put new server endpoints in `app/api/**` as Route Handlers (`route.ts`
  exporting `GET`/`POST`/etc.), matching `app/api/search`, `search/approve`,
  `search/reject`. Don't switch new endpoints to Server Actions — the
  approve/reject flow depends on Route Handlers, and mixing both patterns for
  the same kind of operation would be inconsistent.
- Import via the `@/*` path alias (e.g. `@/lib/oracle`), not relative `../../`
  paths.
- Style with Tailwind utility classes directly in JSX — no CSS modules or
  styled-components. Never hardcode colors; use the semantic tokens defined
  once in `app/globals.css` (`bg-surface`, `text-fg`, `text-fg-muted`, etc.)
  so light/dark mode stays consistent.
- Keep comments minimal — only for non-obvious rationale (a hidden
  constraint, a workaround, why a guard exists), not restating what the code
  does.

## Architecture

- **Frontend stack:** Next.js (App Router) + TypeScript + Tailwind CSS v4,
  `next-themes` for dark mode.
- **API integration:** `exa-js` (the Exa SDK) via `lib/exa.ts`, called only
  from server-side route handlers (`app/api/**`) — never from client
  components, so `EXA_API_KEY` stays server-only.
- **Approve/reject flow:** `POST /api/search` fetches via Exa and stages the
  result server-side (`lib/pendingStore.ts`, in-memory, 30-minute TTL) —
  nothing is written to disk yet. `POST /api/search/approve` appends it to
  `oracle_output.jsonl`; `POST /api/search/reject` discards it.
- **Shared file:** `lib/oracle.ts` resolves `../oracle_output.jsonl` relative
  to `web/` (override via `ORACLE_JSONL_PATH`) — the same file the Python
  script writes, in the same `{source, fetched_at, datapoint, grounding}`
  shape.
- See `web/README.md`'s "Architecture notes" section for two known
  limitations: the pending store is single-process only (won't survive a
  multi-instance or serverless deployment), and dark-mode *toggling* requires
  JS (a CSS `prefers-color-scheme` fallback only covers the initial palette
  for no-JS visitors).
